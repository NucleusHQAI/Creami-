# 01 — Architecture

## Shape of the thing

A static React bundle on Netlify talking directly to Supabase. No server of our own, no API layer to maintain, no deployment story beyond `git push`.

```
  Phone / laptop
        │
        ├── Netlify CDN ──── static build (HTML, JS, CSS, service worker)
        │
        └── Supabase ─────── Postgres  (recipes, batches, everything)
                        └─── Auth      (one shared account, email + password)
```

Row Level Security is what stands between the database and the internet. There is no other gatekeeper, so the policies in `docs/02-data-model.md` matter more than they would in an app with a backend.

## Stack

| Concern | Choice | Version | Why |
|---|---|---|---|
| Build | Vite | 5.x | Fast, boring, no config to speak of |
| UI | React | 18.x | — |
| Language | TypeScript | 5.x | `strict: true` |
| Styling | Tailwind CSS | **3.4.x** | Pinned to 3.4 deliberately — see note below |
| Routing | React Router | 6.x | `createBrowserRouter`, lazy routes |
| Server state | TanStack Query | 5.x | Caching, invalidation, and the offline persistence we need later |
| Database client | `@supabase/supabase-js` | 2.x | — |
| Forms | React Hook Form + Zod | 7.x / 3.x | Zod schemas are shared between form validation and API boundaries |
| Dates | `date-fns` | 3.x | Freeze timers and relative times |
| Icons | `lucide-react` | latest | — |
| Tests | Vitest | 1.x | — |
| PWA | `vite-plugin-pwa` | 0.19+ | Workbox, wrapped |

**On Tailwind 3.4 rather than 4.x:** version 3 uses the JavaScript config file that virtually every code generator, tutorial and model has seen thousands of times. Version 4's CSS-first configuration is better in the abstract, but this project is going to be built incrementally by several different hands, and the cost of one of them writing v3 syntax into a v4 project is higher than the benefit. Pin it in `package.json` and leave it.

Nothing else gets added without a task explicitly calling for it. In particular: no Redux, no MobX, no Zustand, no component library, no animation library. TanStack Query plus one small React context covers the state in this app.

## Data flow

One direction, four layers, no shortcuts:

```
  page/component
      ↓  calls
  feature hook            (features/*/hooks) — TanStack Query lives here
      ↓  calls
  api function            (lib/api) — takes and returns plain objects
      ↓  calls
  supabase client         (lib/supabase.ts)
```

Rules that make this hold together:

- A component never imports `supabase` directly. Not once.
- An api function never imports React and never touches query cache.
- The macro engine takes plain data in and gives plain numbers back. It does not fetch, it does not know what a component is, and it is therefore trivially testable.

### Query keys

Everything in `src/lib/query-keys.ts`:

```ts
export const queryKeys = {
  recipes: {
    all: ['recipes'] as const,
    list: (filters: RecipeFilters) => ['recipes', 'list', filters] as const,
    detail: (id: string) => ['recipes', 'detail', id] as const,
  },
  ingredients: { all: ['ingredients'] as const },
  bases:       { all: ['bases'] as const },
  batches: {
    all:    ['batches'] as const,
    active: ['batches', 'active'] as const,
  },
  shopping: { plan: ['shopping', 'plan'] as const, extras: ['shopping', 'extras'] as const },
  settings: { all: ['settings'] as const },
} as const
```

A mutation invalidates the narrowest key that covers what changed. Favouriting a recipe invalidates `recipes.all` (the list shows favourite state) — it does not invalidate everything.

### Reference data caching

Ingredients, bases and categories change perhaps monthly. Set `staleTime: 1000 * 60 * 60` on them and stop re-fetching a 71-row table on every navigation.

## Authentication

Supabase Auth, email and password, one account.

- **Turn public signup off in the Supabase dashboard before going anywhere near production.** Authentication → Providers → Email → disable "Enable sign ups". With RLS granting access to any authenticated user, leaving signup on means anyone who finds the URL can create an account and read everything.
- Create the household account by hand in the dashboard.
- The app has a single login screen. No signup form, no password reset flow — reset from the dashboard if it ever comes to that.
- Session persists in `localStorage`, which is the Supabase client's default. Sessions are long-lived; nobody wants to log in to look up a recipe.
- `AuthProvider` (in `app/providers.tsx`) exposes `{ session, loading, signIn, signOut }`. While `loading` is true, show a splash rather than flashing the login screen at someone who is already signed in.

## Environment

Two variables. Both are safe in the client bundle — the publishable key is designed to be public, and RLS is what actually protects the data.

```
VITE_SUPABASE_URL=https://<project>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=<publishable key>
```

Commit `.env.example` with the names and empty values. Never commit `.env`. Never put the service role key in this repo, in Netlify's environment, or anywhere else client-side — it bypasses RLS entirely.

Validate both at startup in `lib/supabase.ts` and throw a clear error if either is missing. A blank screen because of a typo'd variable name wastes an hour.

## Deployment

Netlify, connected to this repo.

- Build command `npm run build`, publish directory `dist`.
- Environment variables set in Netlify's UI for the production context.
- A `public/_redirects` containing `/*  /index.html  200` — without it, every deep link 404s on refresh.
- Deploy previews on pull requests; production on merge to `main`.

## Performance targets

Modest, but they are targets:

- Initial JS under 200 KB gzipped. Route-level code splitting via `React.lazy`.
- Recipe list interactive in under 1.5s on a mid-range phone over 4G.
- 40 recipes is a small list — render them all, no virtualisation. Revisit past ~300.
- Google Fonts is the one external dependency. `preconnect`, and `font-display: swap` so text is never invisible.

## Non-goals

No server-side rendering. No API routes. No edge functions. No realtime subscriptions — two people are not going to collide, and polling on focus is enough. No optimistic UI beyond the specific mutations named in `docs/09-pwa-offline.md`.
